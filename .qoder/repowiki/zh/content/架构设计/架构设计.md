## 引言
本架构设计文档面向 AppLab 平台，目标是帮助开发者理解整体设计决策、分层约束和扩展方式。平台基于 .NET 与 Blazor，采用模块化与分层架构，并以低代码元数据驱动页面与应用构建。关键设计原则包括：

- **模块化架构（限界上下文隔离）**：Services 下的 Account、Organization、Approval、Order、SupplyChain、Notification、Setting、BackgroundTask、Testing 等模块按业务域划分；System 下 Enterprise、SystemPortal 作为系统级应用；LowCode 提供设计与渲染能力；Agent/Workbench 提供智能体与工作流能力；Host 仅负责宿主装配。
- **分层架构（Application.Contracts / Application / EntityFrameworkCore / Web）**：每个限界上下文遵循统一分层，契约层独立发布，前端只依赖契约。
- **插件化设计**：仓储实现（JsonFile、EntityFrameworkCore、RemoteService）、主题（AntBlazor）与组件均可插拔替换。
- **ABP DDD 风格**：通过 IAppService 暴露应用服务，结合 HttpClientProxy 在客户端自动生成 HTTP 调用。
- **低代码元数据驱动**：DesignEngine 产出 MetaSchema，RenderEngine 根据元数据动态生成 UI。
- **WebAssembly 懒加载**：LazyModuleRegistry + CompositeServiceProvider 支撑按需注册模块服务。
- **动态 HTTP 代理**：HttpClientProxyInterceptor 拦截 IAppService 方法调用并映射到 ABP 约定 URL。

| 组件 | 职责 | 扩展方式 |

## 详细组件分析

### ABP 分层与 IAppService 契约驱动
平台在每个限界上下文中采用 Application.Contracts → Application → EntityFrameworkCore → Web 的分层：

- **Application.Contracts**：定义 IAppService 接口及 DTO，是前后端共享契约。
- **Application**：实现业务用例，组合领域服务与仓储。
- **EntityFrameworkCore**：实现 DbContext、实体映射与仓储。
- **Web**：暴露控制器或服务端入口，通常由宿主统一装配。

前端通过 IAppService 调用后端，无需手写 HttpClient 调用；服务端则直接解析接口参数并执行业务逻辑。

```mermaid
sequenceDiagram
    participant UI as "UI 层"
    participant Contract as "IAppService 契约"
    participant Proxy as "HttpClientProxyInterceptor"
    participant Convention as "AbpUrlConvention"
    participant Service as "应用服务实现"
    participant Domain as "领域/仓储"
    participant DB as "数据库"

    UI->>Contract: 调用 IAppService 方法
    Contract-->>Proxy: DispatchProxy 拦截
    Proxy->>Convention: 解析方法名与参数
    Convention-->>Proxy: 返回 HTTP 方法与路径
    Proxy->>Service: 发起 HTTP 请求
    Service->>Domain: 执行业务逻辑
    Domain->>DB: 查询或写入数据
    DB-->>Domain: 返回结果
    Domain-->>Service: 返回领域对象或 DTO
    Service-->>Proxy: 序列化响应
    Proxy-->>UI: 返回 Task<T> 结果
```

### WebAssembly 懒加载模块注册：LazyModuleRegistry + CompositeServiceProvider
平台在 WebAssembly 客户端采用懒加载策略：首页只加载必要程序集，其余 Contracts、LowCode 库及第三方依赖在导航到对应路由时才下载。LazyModuleRegistry 管理各路由模块的服务容器，CompositeServiceProvider 提供从根容器到模块容器的服务解析回退，使程序集加载后可以延迟注册服务。

```mermaid
flowchart TD
    Boot["应用启动"] --> LoadMinimal["加载最小程序集"]
    LoadMinimal --> RegisterRoot["注册根服务"]
    RegisterRoot --> Navigate["用户导航到新路由"]
    Navigate --> CheckLazy{"是否需要懒加载程序集？"}
    CheckLazy -->|否| UseExisting["使用已注册服务"]
    CheckLazy -->|Yes| Download["下载程序集"]
    Download --> RegisterModule["LazyModuleRegistry 注册模块服务"]
    RegisterModule --> ResolveWithFallback["CompositeServiceProvider 解析服务"]
    ResolveWithFallback --> UseExisting
```

## 性能与扩展性考量
- **WebAssembly 懒加载**：减少首屏体积，提升加载速度；通过 LazyModuleRegistry 与 CompositeServiceProvider 保证模块加载后服务仍可解析。
- **AOT 与裁剪**：Release 模式启用 AOT 与 Trimming，进一步减小包体积；Debug 模式保留 .pdb 便于调试。
- **元数据驱动渲染**：避免硬编码 UI，降低重复开发成本；但需控制元数据复杂度，避免渲染树过大。
- **动态代理开销**：DispatchProxy 会引入反射与方法解析成本，适合中小规模 API；对高频路径应考虑缓存或优化约定。
- **插件化仓储**：JsonFile 适合本地开发与演示，EFCore 适合生产持久化，RemoteService 支持分布式场景。

## 部署拓扑与系统边界
平台支持两种部署形态：

- **单体部署**：HostAllModule 聚合所有限界上下文、LowCode 引擎与系统应用，适合中小团队或快速交付。
- **微服务部署**：每个限界上下文或服务独立部署，Host 仅负责该服务的装配；RenderEngine 也可独立部署供外部系统消费。

## 跨领域关注点
- **安全**：通过宿主层统一配置认证授权；IAppService 可作为安全校验边界，敏感操作应在服务端验证权限。
- **监控**：建议在 Host 层接入日志、指标与健康检查；RenderEngine 与 DesignEngine 应分别记录元数据加载与渲染异常。
- **配置管理**：RemoteServices 节点统一管理远程服务地址；MetaSchema 存储位置可由 JsonFile、EFCore、RemoteService 切换。
- **错误处理**：HttpClientProxyInterceptor 会在非成功状态码时抛出异常；RenderEngine 应捕获元数据解析错误并提供降级 UI。

## 故障排查指南
- **IAppService 调用失败**：检查 AbpUrlConvention 是否匹配方法命名规范；确认 RemoteServices 地址正确；查看 HttpClientProxyInterceptor 生成的 URL 是否符合预期。
- **WebAssembly 懒加载未生效**：确认 Routes 中是否按路由触发程序集加载；检查 LazyModuleRegistry 是否注册了对应模块服务；确认 CompositeServiceProvider 是否能回退到根容器。
- **RenderEngine 无法渲染元数据**：检查 MetaSchema 是否完整；确认 PageComponentRegistry 是否注册了元数据对应的组件类型；查看 RenderEngineDynamicComponentBase 的组件解析逻辑。
- **仓储实现不一致**：确认当前环境使用的是 JsonFile、EntityFrameworkCore 还是 RemoteService；迁移数据时需确保存储格式兼容。
