## 引言
H.AppLab 是一个基于 .NET 与 Blazor 的企业级应用开发与运行平台。它采用模块化、分层与可插拔的架构模式，既支持单体部署，也支持按服务独立部署。系统围绕“低代码”能力构建，提供可视化设计器、元数据驱动的应用渲染引擎，以及账号、组织、审批、订单、供应链、通知、设置、测试等基础与企业服务，同时通过 SystemPortal 和 Enterprise 面向平台运营与管理。

该平台的核心目标是：
- 以低代码方式快速定义页面与组件，生成并运行应用。
- 通过统一宿主聚合各业务模块，形成一致的前端体验与后端 API。
- 通过 HttpClient 动态代理与约定式路由，让前端只依赖接口契约，屏蔽 HTTP 调用细节。
- 通过多租户机制支撑企业隔离的数据访问。
- 通过 WebAssembly 懒加载与压缩策略提升前端启动与运行性能。

## 项目结构
仓库采用解决方案级组织方式，核心目录包括：
- Host：宿主程序，负责 Blazor Server/WebAssembly 组合渲染、SignalR、认证授权、多租户、控制器注册、静态资源与中间件管道。
- Components：跨应用复用的 UI 组件，如 AppDrawer。
- LowCode：低代码核心领域，包含 Common 公共元数据与组件基类、DesignEngine 设计引擎、RenderEngine 渲染引擎。
- Services：按限界上下文划分的业务服务，每个服务通常包含 Application.Contracts、Application、EntityFrameworkCore、Web 四个层次。
- System：系统级应用，如 Enterprise、SystemPortal，用于平台运营。
- Tools：每个服务的数据库迁移工具。
- Utils：通用工具库，包括 ABP 应用契约封装、HTTP 客户端代理、Blazor 工具、ID 生成与基础类型扩展。

| 组件 | 职责 | 关键实现要点 |

## 架构总览
H.AppLab 的整体架构可以概括为“统一宿主 + 模块化业务 + 低代码引擎 + 前端契约驱动”。

- 表现层：Blazor Server + WebAssembly 混合渲染，前端通过路由懒加载不同应用的程序集。
- 应用层：ABP 应用服务，按限界上下文划分为多个 Service 模块。
- 领域层：各模块 Domain 实体与规则，部分由 EntityFrameworkCore 映射到数据库。
- 基础设施层：数据库迁移、仓储实现、配置、远程服务、HTTP 代理、SignalR、Hangfire 等。

## 分层与模块化架构
### 分层架构
系统遵循典型的四层结构：

| 层级 | 说明 | 在系统中的体现 |
| --- | --- | --- |
| 表现层 | 用户界面与交互逻辑 | Blazor Server + WebAssembly；AppDrawer、各 Web 模块的 Razor 组件 |
| 应用层 | 业务流程编排与对外 API | 各模块的 Application 与 Application.Contracts，如 AccountApplicationModule |
| 领域层 | 领域模型与业务规则 | 各模块 Domain 实体与行为 |
| 基础设施层 | 持久化、配置、远程调用、消息、调度等 | EntityFrameworkCore、DbMigrator、HttpClientProxy、SignalR、Hangfire |

### 模块化架构
每个业务模块遵循统一的模块结构：
- Application.Contracts：对外暴露的 DTO 与应用服务接口。
- Application：应用服务实现。
- EntityFrameworkCore：数据库上下文、实体、迁移。
- Web：Web 层入口与模块注册。

统一宿主通过 HostAllModule 聚合所有模块，避免硬编码业务耦合，同时集中配置认证、多租户、控制器与传统 MVC 约定。

## 低代码架构：设计与渲染引擎
### 设计理念
低代码架构以“元数据驱动”为核心：
- 设计阶段：DesignEngine 提供可视化编辑器，用户编排页面、组件、事件与数据源，最终输出应用元数据。
- 运行阶段：RenderEngine 读取元数据，动态渲染出可运行的应用，并通过主题系统适配界面风格。

### 元数据与组件体系
- Common 中的 MetaSchema 定义元数据结构，供设计器与渲染器共用。
- ComponentBase 与 Components 提供组件基类与默认组件库，降低自定义组件开发成本。
- 仓储层支持 JsonFile、EntityFrameworkCore 与 RemoteService 三种实现，满足本地、数据库与远端三种存储场景。

```mermaid

    Save --> Store{"选择仓储实现"}
    Store -->|JsonFile| JsonStore["JSON 文件存储"]

```

## 安全架构
### 认证与授权
- 宿主使用 Cookie 认证，配置了普通登录路径与系统登录路径两套 Scheme。
- 未登录时重定向到 /account/login 或 /system/login。
- CSRF 保护针对 WASM 关闭自动验证，依赖 SameSite Cookie 提供基础防护。

## 依赖关系分析
### 前端契约到 HTTP 的动态代理
前端通过 AddHttpClientProxies 扫描 IAppService 接口，使用 HttpClientProxyInterceptor 将方法调用转换为 HTTP 请求。URL 构造遵循 ABP 约定：
- 接口名去掉 I 前缀与 AppService/ApplicationService 后缀，转为 kebab-case。
- 方法名前缀决定 HTTP 动词，例如 GetList → GET，Create → POST。
- id 参数与以 Id 结尾的参数会被放入 URL 路径段。
- 复杂参数在 POST/PUT 时放入请求体，GET/DELETE 时可展开为查询参数。

```mermaid
flowchart TD
    Call["前端调用 IAppService 方法"] --> Intercept["DispatchProxy 拦截"]
    Intercept --> Convention["AbpUrlConvention 解析控制器与方法"]
    Convention --> BuildUrl["构建 URL 与参数"]
    BuildUrl --> Send["HttpClient 发送请求"]
    Send --> Response["接收并反序列化响应"]
    Response --> Return["返回给前端调用方"]
```

## 故障排查指南

## 结论
H.AppLab 通过统一宿主、模块化业务、低代码设计与渲染引擎、前端契约驱动与多租户机制，形成了一个可扩展、可复用、可运维的企业级应用平台。其架构优势体现在：
- 清晰的层次与模块边界，便于团队分工与独立演进。
- 低代码能力覆盖从设计到运行的完整链路，降低应用开发门槛。
- 前端契约驱动与动态代理减少重复 HTTP 调用代码，提升一致性。
- 多租户与认证授权为多企业场景提供基础安全保障。
- 懒加载与压缩策略优化前端启动与运行体验。

在实际使用中，建议：
- 新增业务模块时遵循 Application.Contracts / Application / EntityFrameworkCore / Web 的分层规范。
- 谨慎扩展多租户与认证逻辑，确保 Claim 与租户上下文一致性。
- 合理拆分远程服务，利用 RemoteServices 配置实现单体到微服务的平滑过渡。
- 充分利用低代码元数据与组件体系，提高页面与功能的复用率。
